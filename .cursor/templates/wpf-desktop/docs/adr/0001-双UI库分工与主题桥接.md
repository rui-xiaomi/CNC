# 双 UI 库分工：WPF-UI 主 + HandyControl 补

> 仅当目标项目真实采用 WPF-UI + HandyControl 时使用本 ADR。提交前填写两个包的锁定版本，并在该版本下验证资源键、浅/深主题切换和 UI Automation。

| 依赖 | 锁定版本 |
|---|---|
| WPF-UI | 待确认 |
| HandyControl | 待确认 |

WPF-UI 的 Fluent 外观和主题体系符合我们对 Windows 11 原生观感的要求，但缺少业务型控件（分页、日期时间选择、多选下拉、空状态、步骤条）；HandyControl 业务控件齐全但视觉风格偏旧。因此决定 **WPF-UI 承担外壳、主题与全部基础控件，HandyControl 只用于 WPF-UI 确实没有的控件**，并通过一层桥接资源字典把 HandyControl 的语义色键重定向到 WPF-UI 的画刷，使两者在深浅色下保持一致。

## 被否决的备选方案

**只用 WPF-UI。** 分页、日期时间、多选下拉需要自己实现，估算成本高于引入第二个库，且自研控件的可访问性属性容易缺失，会影响后续 UI 自动化测试。

**只用 HandyControl。** 控件够用，但视觉风格与产品定位不符，且它的主题体系（SkinType）扩展性弱于 WPF-UI 的 `ApplicationThemeManager`。

**改用商业控件库（DevExpress / Syncfusion）。** 一步到位，但授权成本高，且深度绑定后迁移成本极大——属于典型的"换掉要花一个季度"的锁定。当前项目的数据密度未达到需要商业级 DataGrid 的程度。

**两库平等使用、各取所长。** 这是最初的直觉方案，被明确否决：同一种交互在不同页面用不同库的控件，会导致视觉不一致，并且 UI 自动化测试需要为同一语义写两套选择器。因此确立了单向仲裁规则——**同一需求两库都有时一律用 WPF-UI**。

## 后果（非显而易见的部分）

**资源字典合并顺序是有意为之，不要"优化"。** 顺序必须是：HandyControl → WPF-UI → 桥接层。两个库都为原生控件（`TextBox` / `ComboBox` / `Button` 等）注册隐式样式，后合并者胜出；WPF-UI 必须在后，否则外壳的 Fluent 观感会被 HandyControl 的隐式样式覆盖。看到这个顺序觉得"HandyControl 是补充库为什么排在前面"的人，请先读这一段。

**主题切换必须成对执行。** `ApplicationThemeManager.Apply()` 只切 WPF-UI，HandyControl 的皮肤需要单独切换，且桥接字典要在其后重新合并一次。已封装为统一入口，业务代码禁止单独调用任一库的主题 API。

**`MessageBox` 现在有三个来源**（`System.Windows`、`ui:`、`hc:`）。统一只用 `ui:MessageBox`，通过 `DialogService` 封装，另外两个在代码审查中禁用。

**升级任一库需要重新核对桥接字典。** 两个库都改过资源键名。库版本变更时，`Themes/HandyControlBridge.xaml` 与 `DESIGN.md` §2.2 的键名对照表必须一起验证。

**HandyControl 的原始色板键（如 `DarkPrimaryBrush`）禁止直接引用**，只能使用 `DESIGN.md` §2.2 中已列出的、经过桥接的语义键——直接引用会绕过桥接层，在切换主题时出现颜色不同步。

具体的控件仲裁表与桥接实现见 `docs/design/DESIGN.md` §2.3 与 §5。
