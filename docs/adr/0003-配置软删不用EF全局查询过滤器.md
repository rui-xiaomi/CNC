# 配置软删不使用 EF 全局查询过滤器，保留调用方显式判活

- 状态：Accepted
- 日期：2026-09-04

## 背景

配置实体（WorkLine / Craftwork / Equipment / Position / Plc / PlcPoint / FrameBind / LOCATION_MAP / Agv）
用 `STATE='0'/'1'` 做软删，判活条件在 Data 层被手写数十处。架构评审很自然会提出用
`CncDbContext.OnModelCreating` 加 `HasQueryFilter(e => e.State == "0")` 一次收口。

本次评审确认：**不能这么做**。

## 决策

软删过滤保持由调用方显式表达，不引入 EF 全局查询过滤器。收口只做两件事：

1. 判活语义的唯一定义是 `CncLoader.Core.Config.ConfigActivity`（`Active`/`Disabled`/`IsActive`）；
   Data 层的 `ConfigFlags` 转发到它，字面量 `"0"` 不再在各仓储里重复出现。
2. 引用校验与软删收进同一 `DbContext` + 同一事务（`ConfigSoftDelete.RunAsync`）。

## 被否决的理解（易误判）

**把全局过滤器当成纯粹的重复消除。** 它会改变可观察行为：全局过滤后，已禁用的行与不存在的行
在查询结果里都表现为「查不到」。而 `RoutingAvailabilityValidator` 的 fail-closed 诊断必须区分
`NotFound`（关系缺失，配置错）与 `EquipmentDisabled` / `CraftDisabled` / `WorkLineDisabled`
（人为停用），现场排障和 UI 文案都依赖这个区分，`RoutingSoftDeleteQueryTests` 的 33 个用例
也逐条锁定了原因枚举。加全局过滤器等于把这些原因全部塌缩成 `NotFound`。

**把 `*RoutingStore` 的「不过滤」当成漏了过滤。** `EquipmentRoutingStore` /
`LocationMapRoutingStore` / `PlcPointRoutingStore` 刻意原样返回含 `STATE` 的行，
判活权交给上层——这是让上层能 fail-closed 且给出准确原因的前提，不是缺陷。
全局过滤器会让这些 store 无法再拿到被停用的行。

**指望用 `IgnoreQueryFilters()` 打补丁。** 那意味着安全关键路径全部要记得加这一句，
漏一处就静默退化成「禁用等于不存在」——把显式约束换成了约定，方向相反。

## 结果

- 判活条件仍需在查询里写出来，但字面量只有 `ConfigActivity.Active` 一个来源。
- 表达式树里必须与常量比较（`x.State == ConfigActivity.Active`），不能调
  `ConfigActivity.IsActive(x.State)`——后者 EF Core 无法翻译成 SQL。内存遍历处才用方法形式。
- 新增配置实体时，判活与删除都照抄现有仓储的形状；删除走 `ConfigSoftDelete.RunAsync`。
- 若将来确实需要全局过滤器，须先给出如何保留「禁用 vs 不存在」区分的方案，并同步改
  `RoutingUnavailableReason` 与其测试，再新开 ADR 覆盖本条。
